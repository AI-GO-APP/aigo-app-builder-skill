# Hosted App 遷入作業手冊（從 PaaS 搬到 Hosted App：盤點、測試、切換、退場）

> 什麼時候讀：`migration-workflow.md` §2.1 判定走 **Hosted App** 的遷入案。Custom App 線有 SKILL.md 的
> Phase 1～5，Hosted 線不進 Phase 2–4——**本檔就是 Hosted 遷入的主流程**：每個階段做什麼、讀哪一節、
> 跑哪支腳本、什麼條件才能往下走。細節不在這裡重寫，都指回原章節；順序以本檔為準
> （`migration-workflow.md` §2.6 A 的「切換順序」是摘要）。
>
> 每個階段的「通過條件」沒全過，不進下一階段；做不到的項目要寫進計畫，並由 owner 簽核接受風險。
> 標 **［負責人］** 的步驟由有權限的人執行或逐項核准：密鑰值、第三方後台、舊平台、正式環境的寫入與開關。
> AI 列規格、準備指令、做只讀驗證，**不自己動手**。

## 0. 開始前：先確認真正的正式站在哪

遷入期間同時存在好幾個環境：原平台的正式站、AI GO 上的新正式 Hosted、UAT，有時還有本機。
它們跑的版本常常不同，**拿 A 環境的現象替 B 環境下結論**是這類專案最常見的誤判
（例：以為「正式排程有在跑」，其實那是新站，使用者實際用的仍是原平台）。

任何排錯、測試、下結論之前，先寫下這三行，放進計畫並隨時更新：

- 每個環境跑哪一版：commit 或 version marker（`hosted-apps.md` §3.4），不是「最新那版」
- 使用者實際連到哪一邊：網域的 DNS、OAuth 回呼、第三方登記（`migration-workflow.md` §2.6 A）指向誰
- 每個環境的資料從哪來、何時同步過：正式複本（哪天）／空庫＋測試資料／原平台即時資料

版本不同的兩個環境不能互相佐證；要比對就先把版本拉齊。

## 2. 階段 A：盤點

照 `migration-workflow.md` §2.0 → §2.2 做，產出下面七項（放進計畫，之後每個階段都會回來對照）：

1. **技術組成與原拓撲**：前後端、資料、雲端服務誰連誰（`migration-workflow.md` §2.0）
2. **repo 外的東西**：留在同事電腦、內網 VM 的排程與微服務，每支的落點與切換順序（`migration-workflow.md` §2.0）
3. **env 對帳表**：四個來源盤出全部 key，標目標位置與處置（`hosted-apps.md` §4）。原平台的 env 設定頁由
   **［負責人］**匯出 **key 名稱**，值不進對話
4. **外部登記項**：誰會從外面打進來、登記在哪、誰有權改（`migration-workflow.md` §2.6 A）
5. **寫死的正式資源**：舊平台網域、env 讀取帶預設值、寫死的雲端資源 ID（`migration-workflow.md` §2.6 B）
6. **資料與登入落點**：
   - 資料**預設進平台表**（`hosted-apps.md` §7.1，原 DB 退場）。要走外接 PostgreSQL，必須已有規則 32 的
     **平台核准紀錄**（issue 編號、日期、核准工程師；`dev-rules.md` 規則 32）——沒有就視為不存在，owner 只能同意去申請，不能自己決定
   - 檔案進平台 App 檔案（`hosted-apps.md` §5.2）；`/data` 只放非業務資料（`hosted-apps.md` §7）
   - 登入沿用 AI GO 或維持自家：由客戶與 PO 決定（`migration-workflow.md` §2.4.5、`member-admin.md` §7.1）。
     自家登入時人員名冊在哪、AI GO 登入時名冊怎麼對到租戶成員，要跟資料落點一起定。原系統登入若是 Supabase Auth
     這類 BaaS 認證，不在規則 32 例外範圍內（例外不含 Auth），「維持自家登入」要先問平台
   - 選用 AI GO 登入、又保留自家認證後端的，照 `dev-rules.md` 規則 34 做即時撤權
   - **入站路徑**：Hosted 會不會被伺服器對伺服器地打進來（平台排程的轉發 action、webhook、推送訂閱）？
     會的話 Hosted 要 `public`、由 app 自己驗金鑰或簽章（`hosted-apps.md` §2.1、§5.1）；`internal` 會擋掉這些請求
     （`hosted-apps.md` §6）。選用 AI GO 登入（`internal`）又需要入站的，入口路徑沒有平台定案前列為**阻塞**，先問平台，不要自創做法
   - 已核准外接 PostgreSQL 的，env 對帳表要多一顆新的連線字串 env（寫法照 `hosted-apps.md` §7.2），由［負責人］填——
     這是 `hosted-apps.md` §4「原系統的 `DATABASE_URL` 不要搬」的例外，對帳表註明，不要標成「不搬」
7. **UAT 結論一句**（`dev-rules.md` 規則 33）：`UAT＝有；拓撲 X` 或 `UAT＝無；理由 Y；風險 Z`

**通過條件**：七項都有；env 對帳表是四個來源的聯集，不是「記得的那幾顆」；資料落點符合規則 32；
登入方式、入站路徑與 UAT 結論已寫進計畫，沒有未解的阻塞。

## 3. 階段 B：常駐 PaaS 的隱藏假設掃描

原平台（Zeabur、Render、Railway、Heroku、自架 VM 一類）的容器通常**一直開著、只有一份**。程式在那種環境下
默默依賴的事，搬到 Hosted App（閒置縮到零、最多 2 個實例、單請求 300 秒，`hosted-apps.md` §2）就不成立了，
而且多半不報錯。逐列掃：

| 隱藏假設 | 怎麼找 | 在 Hosted 上的症狀 | 落點 |
|---|---|---|---|
| 行程內計時器會一直跑 | `setInterval`、node-cron、APScheduler、框架啟動鉤子（`instrumentation`、`on_startup`）裡的 loop | 縮到零後排程全停 | 平台排程 → 轉發 action（`hosted-apps.md` §2.1） |
| 回應送出後還能繼續做事 | 先回 202 再背景跑、`void promise`、回應後才寫日誌或發通知 | 偶爾少做一次、無錯誤 | 請求內做完、長任務切段（`hosted-apps.md` §2.1） |
| 記憶體裡的狀態只有一份 | 記憶體 session、快取、佇列、限流計數、防重放 nonce | 一半請求變未登入、限流與防重放失效 | 落平台表（規則 32 例外核准後才可落外接庫）（`hosted-apps.md` §2） |
| 本機檔案會留著 | 上傳目錄、SQLite、產生的檔案、把 `/tmp` 當長期存放 | 重啟或換實例後檔案消失 | 檔案 → 平台 App 檔案（`hosted-apps.md` §5.2）；業務資料 → 平台表；`/data` 只放非業務狀態（`hosted-apps.md` §7）。**不要把 SQLite 放 `/data`**：最多 2 個實例共用同一個掛載 |
| 同一件事只有一個行程在做 | 記憶體鎖、單例工作、「啟動時搶 leader」 | 兩個實例各做一次 | DB 唯一鍵佔用（`hosted-apps.md` §2.1） |
| 請求可以很長、連線可以一直開 | 匯出、報表、SSE、WebSocket | 300 秒必斷、504 | 切段、client 自動重連（`hosted-apps.md` §2） |
| 啟動只發生一次 | 開機時跑 migration、預熱大型快取 | 每次冷啟動都做一次；2 個實例同時啟動會同時跑 | `hosted-apps.md` §3.2 的部署流程沒有 release／pre-deploy 這一步（未核實是否有替代機制）。平台表的 schema 由資料中心建表，不在開機跑；外接庫的 migration 由［負責人］在本機對外接庫執行；真要留在啟動時跑，做成冪等並加 DB 鎖。快取改按需載入 |
| 出站 IP 固定 | 第三方 IP 白名單 | 對方直接拒絕連線 | Hosted 有沒有固定出站 IP：**未核實**，先問平台；退路是請對方改用 token 或簽章驗證，或這支整合留在原機 |
| 憑證是本機檔案 | `*_CREDENTIALS=/path/key.json` 這類路徑型 env | 依賴它的功能全失敗 | 改值型 env（`hosted-apps.md` §4） |
| 綁定位址照框架預設 | 以 `HOSTNAME` 決定 bind 的框架 | 探針連不上、啟動失敗 | `ENV HOSTNAME=0.0.0.0`（`hosted-apps.md` §2） |

另外兩項程式改動：
- **切換前只放行名單**：Hosted 是 `public`（自家登入或要被打進來）時，正式使用者在切換前就連得到新站，兩邊會同時有寫入。
  app 要有一個開關（env 或設定列），切換前只放行建置者與測試者，切換當天才關掉
- **寫入閘（維護開關）**：回滾時要能一次擋住所有寫入，包括 webhook、推送、轉發 action 這類靠金鑰進來的入站端點（本檔 §8 回滾第 1 步）

**通過條件**：每一列都寫了「原系統有沒有、在哪、落點是什麼」；要改程式的（含切換前只放行名單、寫入閘），改動寫進計畫。

## 4. 階段 C：建新站、UAT、首次資料匯入

1. 依 `hosted-apps.md` §3 部署新正式 Hosted；過 §3.0 `always_on` 決策閘
2. **可見度先收緊**：新正式在切換前只放行建置者與測試者——
   - `internal` 的：`access_role_ids` 只含這些人的角色（`hosted-apps.md` §6、`member-admin.md` §3）。
     AI 可以改 `access-settings`（不經手密鑰；body 照 `hosted-apps.md` §6 的必帶欄位）
   - `public` 的（自家登入，或要被打進來，見階段 A 第 6 項的入站路徑）：用 §3 的「切換前只放行名單」開關
   - **先定好再 clone**：clone 會帶走 `visibility`、`access_role_ids`（`uat-environment.md` §3 步驟 2）
3. 依 env 對帳表設定 runtime-settings（**［負責人］**填密鑰值）；要沿用原值的密鑰照 `hosted-apps.md` §4「不可隨手換新」
4. 有排程的：照 `hosted-apps.md` §2.1 建好轉發鏈的前置——入口 Custom App 與轉發 action、Hosted 的端點與共享金鑰驗證
   （Hosted 必須 `public`，`internal` 會擋掉轉發，見第 2 步）；
   **外部服務 slug 與 `ctx.secrets` 的金鑰由［負責人］設定**（`custom-app-dev-guide.md` §25.2）。平台排程本身先不建（本檔 §8 第 8 步）
5. 階段 A 第 5 項的防線（非正式環境沒設就報錯）**先部署到新正式的現行版次**，再 clone 出 UAT
   （`uat-environment.md` §3：clone 帶的是正式版次與正式 env）
6. 依 `uat-environment.md` 建 UAT（`UAT＝無` 的略過）；資料照本檔 §5。
   - **clone、白名單重建 env、`access-settings` 三個動作連成一段，由［負責人］執行或在場逐項核准，中間不停頓**——
     clone 出來的 pod 會帶著正式 env 先跑起來（`uat-environment.md` §3 步驟 2–3），env 又是［負責人］才能動的，
     AI 不能先 clone 再等人。AI 只準備 key 清單（不含值）與各段 body，不單獨呼叫 `POST /clone`
   - 階段 A 判定需要入站的：UAT 維持 `public`、`access_role_ids` 留空，靠金鑰驗證與「切換前只放行名單」開關（UAT 設成只放行測試者）
     限制，不照 `uat-environment.md` §3 步驟 2 改成 `internal`——否則轉發 action、單支觸發、webhook 測試全部被擋
   - **預設表一個租戶只有一份**：UAT 讀寫預設表就是讀寫正式表（規則 33 不允許），`uat-environment.md` §2 的分開只涵蓋自建表。
     用到預設表的功能在 UAT 怎麼測，列為待決策問平台或 PO，不得讓 UAT 寫進預設表
7. **首次資料匯入**（歷史資料，`UAT＝無` 的略過）：
   - 平台表：先過 `migration-workflow.md` §2.5 的映射確認閘門；目標預設表掛簽核流程的，匯入前照 `custom-app-dev-guide.md` §23.1
     處置（批次匯入會逐筆開簽核單）；建好舊 ID ↔ 平台 UUID 的對照表並保存（回滾時反向回寫要用）。
     估時程照實際走的路徑：在容器內經 Open Proxy 是每分鐘 600 次（`hosted-apps.md` §5）；本地腳本或匯入 action 照
     `custom-app-dev-guide.md` §23.6
   - **落預設表的，首次匯入就是寫進正式**：歷史資料會立刻出現在租戶的其他 app 與 ERP 裡，時點要 owner 同意
   - 使用者相關欄位（選用 AI GO 登入時要以平台 user id 當 key，`member-admin.md` §7）：成員到階段 E 才由客戶邀請，
     首次匯入時先以信箱暫存，最後同步時再換成 user id；或把這類欄位留到最後同步才匯入
   - **檔案**：照 `hosted-apps.md` §5.2、§7.1 在容器內搬進平台 App 檔案（一次性匯入端點，跑完移除），資料列改存 `file_id`；
     舊檔案 key ↔ `file_id` 也進對照表；先估總量（單檔與配額上限見 §5.2）
   - 外接 PostgreSQL（已核准者）：照 `hosted-apps.md` §7.2（匯入走 session 模式或直連、權限保底）
   - 匯入由［負責人］核准後執行；完成後核對筆數與關鍵表
8. 檢查（只讀腳本，不印值）：
   - `scripts/aigo_env_diff.py --a <新正式 hosted-id> --b <uat hosted-id>`：密鑰類不得兩邊相同
   - `scripts/aigo_env_diff.py --app <新正式 hosted-id> --expect <清單>`：缺的 key 列給［負責人］。清單只放對帳表裡
     目標位置是 runtime-settings、處置不是不搬／退役的列，不放 `AIGO_*`、`PORT`
   - `scripts/aigo_cron_health.py --app <uat 入口 app-id>`：**輸出零條排程**（結束碼 0 只代表沒有紅燈，不代表零條）
   - `UAT＝無` 的略過第一項（`--a/--b` 比對）與第三項（UAT 排程檢查）

**通過條件**：新正式與 UAT 除「env 尚缺清空」外都過 `hosted-apps.md` §3.4——尚缺必須在階段 E 結束前清空，§8 第 4 步再驗一次；
`uat-environment.md` §4 驗證表中**適用於本案 UAT 結論與拓撲的項目**全過（`UAT＝無` 的不適用；「403 對照」會讀預設表，
與第 6 步「UAT 不碰預設表」衝突：只能改用 UAT 專用、掛有 `$user.*` 規則的自建表或測試表驗，**不得寫進或讀取任何預設表**
（規則 33 是硬規則，owner 核准也不能豁免）；平台不支援這種做法的，這一項列為待決策問平台，不在 UAT 驗）；首次匯入的筆數核對通過；上面的檢查乾淨。

## 5. UAT 測試資料策略

**先判斷**：手上的 UAT 資料是不是正式複本？裡面有沒有真人名冊、使用者授權 token、推播訂閱、
第三方對象（聊天群組、行事曆活動、外部系統的 ID）？有任何一項，**預設重建空庫再塞測試資料**，
不要在複本上原地清——漏清一處，UAT 的功能就會打到真人或正式系統。

把資料表分五類，決定每類怎麼處理：

| 類別 | 例 | 處理 |
|---|---|---|
| 設定類（不含個資） | 範本、選項清單、模組設定、權限定義 | 從正式匯入（逐表白名單，由 owner 核對） |
| 個資類 | 人員名冊、聯絡方式、對話內容 | 不匯入，改塞測試人 |
| 憑證類 | 使用者授權 token、API key、簽章金鑰、裝置金鑰 | 不匯入。UAT 的解密金鑰應該不同，匯了也解不開；若 UAT 誤用和正式同一把金鑰，就解得開正式憑證，等於外洩 |
| 第三方對象 | 推播訂閱、聊天綁定、行事曆活動 ID、外部系統的單號 | 不匯入，用測試資源重建 |
| 衍生紀錄 | 執行紀錄、佇列、快取、統計 | 不匯入，讓 UAT 自己產生 |

步驟：

1. **先止血**：UAT 的排程總開關維持關；**［負責人］**清掉或換掉會碰到正式的 env（資源 ID、推播金鑰、第三方 webhook）——
   `PUT runtime-settings` 是全量替換（`hosted-apps.md` §4），等於經手所有密鑰值，AI 不代做
2. **重建空庫**：用 app 自己的開站流程或 schema 建立，第一個管理員只放建置者
3. **匯入設定類**：照上表白名單；排除排程開關、通知名單、正式公司代碼這類「環境專屬」的設定列
4. **塞測試資料**：一間測試公司（app 有沙盒或測試公司機制就用）、3～5 個測試人（不同角色）、
   每個核心物件幾筆假資料，涵蓋要測的狀態（草稿、進行中、已完成、已取消）
5. **外部測試資源**（**［負責人］**準備，一項一個 owner）：測試用的 Google／Microsoft 帳號（加進 OAuth 測試使用者）、
   測試共用雲端硬碟、測試訊息平台官方帳號加一支測試手機、測試 GitHub 帳號與 repo、測試表單或腳本、
   UAT 專用的推送主題與訂閱——都不要指向正式那一份（`migration-workflow.md` §2.6 A）
6. **建資料腳本**：可重跑、冪等；**啟動時檢查目標是 UAT**（網址含 `-uat` 或明確的環境 env），否則拒絕執行；
   只寫 UAT，不讀正式的個資

真的只能原地清時，至少清：個資換成假的、使用者授權 token、聊天綁定與頻道密鑰、推播訂閱、通知名單只留測試對象、
連接器與簽章金鑰、裝置金鑰、對話內容、第三方活動 ID、佇列與執行紀錄——清完用 `uat-environment.md` §4 再驗一次。

## 6. 階段 D：功能測試

用 `resources/hosted_migration_test_plan_template.md`：每個功能一段，寫「問題／現況／怎麼修／怎麼在 UAT 測／誰做」。
功能的切法照**對外依賴**，不照頁面：登入、核心資料、排程、每一個外部整合（訊息平台、雲端硬碟、行事曆、金流、寄信……）
各自一段。

測試順序（前面不過，後面不測）：

1. **安全前置**：§5 的止血與重建、階段 A 第 5 項的防線已上
2. **登入**：名冊內可進、名冊外被擋、登出再登入、權限隔離
3. **核心資料**：新增、修改、刪除、權限；站外連結（通知、信件裡的連結）開得到頁面
4. **只動資料庫的排程**：一次一支、單支手動觸發（不佔正式時段，`hosted-apps.md` §2.1）
5. **對外整合**：一次一個，目的地都是 §5 的測試資源；每一項驗兩件事——測試對象**真的收到**，正式那一側**沒有任何變化**
6. **會碰外部的排程**：照 `hosted-apps.md` §2.1「排程最後才開」，owner 確認後才在 UAT 建平台排程、開總開關

每一項的結果寫回模板：通過／失敗（附現象）／已知問題（附 owner 與處置）。

**通過條件**：每一列「通過」，或列為已知問題且 owner 簽核接受；所有「會碰到真人或正式系統」的功能都至少用測試對象跑過一次。

## 7. 階段 E：切換準備

- **切換清單**：`migration-workflow.md` §2.6 A 的每一項外部登記，寫「登記在哪、誰改（［負責人］）、改成什麼、第幾步改、
  怎麼驗證、怎麼改回去」
- **名冊與角色**：選用 AI GO 登入的，正式使用者在切換前就要是租戶成員並掛好 app 角色——由**客戶**邀請
  （`member-admin.md` §7.1），並做「app 可登入名單 vs 租戶成員」對照，切換當天再對一次。自家登入的，確認正式名冊已在新庫
- **自訂網域**（Hosted 才有，`hosted-apps.md` §9；建網域與到網域商設記錄由［負責人］做，`POST domains` 是 session-only）：
  理想狀態是網域已建好、已過 `pending_cert`，DNS 還沒改指向——但 §9 的 `records[]` 是否把憑證驗證記錄和指向記錄分開
  **未核實**，先問平台；做不到時把憑證簽發的等待時間算進凍結時段。
  對外網址 env（`APP_URL`、`NEXT_PUBLIC_*` 這類標 `both` 的）改成最終網域後要**重新建置部署**（`hosted-apps.md` §4 驗證步驟）；
  改完之後就不能再用 `*.ai-go.app` 驗 OAuth，相關驗證要在改設定之前做完。OAuth redirect URI 加上最終網域
- **env 尚缺清空**：`scripts/aigo_env_diff.py --app <新正式> --expect <清單>` 乾淨（清單範圍同 §4 第 8 步）
- **新正式部署 UAT 測過的同一版**，並用 version marker 確認
- **資料同步方式**（`UAT＝無` 的略過）：選定「全量重灌」或「差異補寫」並寫出依據。**落預設表的一律差異補寫**——
  全量重灌要刪掉重建，UUID 全換、其他 app 的引用會斷、簽核流程會再觸發。檔案同樣分全量或差異，照 §4 第 7 步的方式
- **同步演練**：用**去識別化或合成、與正式同量級的資料**灌進 UAT，演練一次匯出 → 匯入 → 核對（含檔案），量出耗時——
  這是凍結時段長度的依據。真資料演練要先有合法落點：外接庫的第三顆庫需要平台核准；平台表要寫明表名、可見角色、刪除時點並經 owner 同意。
  拿不到就不做真資料演練。**落預設表的部分不在 UAT 演練**（UAT 不得寫預設表）：只演練自建表與檔案，
  預設表的耗時用首次匯入的實測值推估，或列為待決策問平台
- **日期與凍結時段**：選使用量低的時段；凍結期間原站**唯讀或停機**，最後一次同步之後不能再有新寫入。
  原站真的停不了寫入的，要在這裡選定並演練「抓變更＋衝突處理」的方式（哪些表、怎麼找出凍結後的變更、兩邊都改過時以誰為準），
  演練不過就不能切
- **回滾**：寫清楚「出現什麼就切回去」（例：登入失敗、核心流程不通、資料筆數對不上）、誰下決定、多久內決定；
  **新站期間寫入的資料**選一種處理並寫進計畫——
  1. 反向回寫原平台的 DB：平台表與外接 PostgreSQL 都一樣，是把新站期間的寫入回寫到**原系統的庫**。已存在的列用
     §4 第 7 步的對照表反查；新站才建立的列在原庫沒有舊 ID，回寫時由原庫配號並補進對照表
  2. 人工補登（量小時）
  3. 凍結時段短、接受遺失，由 owner 簽核
- **回滾演練**：在 UAT 用測試登記走一次「擋寫入（含入站端點的寫入閘）→ 改指向 → 改回」，記下耗時；選了反向回寫的，再演練一次「新站寫入 → 回寫 → 核對」，回寫目標是原庫的還原複本或測試庫，**不得對線上原庫演練**
- **通知使用者**：切換時段、要重新登入或重新連結的項目、出問題找誰

**通過條件**：上面每一項都寫進計畫；資料同步與回滾都演練過一次且時間可接受。

## 8. 階段 F：切換當天

依序做，每一步做完當場驗證再往下。AI 只做只讀驗證與準備指令；標［負責人］的由負責人執行或逐項核准：

1. **［負責人］公告開始、凍結原站寫入**（唯讀或停機）；停不了寫入的，照階段 E 演練過的「抓變更＋衝突處理」方式進行
2. **［負責人］停掉原站的排程**，以及留在原機、會寫資料的排程與微服務（階段 A 第 2 項）
3. **最後一次資料同步**：先確認原站已無新寫入、剩餘變更已全數抓出，再同步（［負責人］核准後執行；照階段 E 選定的全量或差異、`migration-workflow.md` §2.5 閘門）：
   匯出 → 匯入 → 核對筆數與關鍵表；檔案照 §4 第 7 步補差異；使用者欄位從信箱換成 user id。`UAT＝無` 的不搬資料、只切運算層
4. **新正式最後確認**（只讀）：`scripts/aigo_env_diff.py --app <hosted-id> --expect <清單>` 乾淨；version marker 是要上的那版
5. **［負責人］放行正式使用者**：`internal` 的把正式角色加進 `access_role_ids`（`hosted-apps.md` §6、`member-admin.md` §3），
   AI GO 登入的再對一次名冊；`public` 的關掉「切換前只放行名單」開關（本檔 §3）
6. **［負責人］逐項改外部登記**：照切換清單的順序，每改一項就驗一次（webhook 收得到、OAuth 登得進、推送有進來）；
   有自訂網域的，在這一步改 DNS
7. **冒煙測試**：用**最終網域**；登入、核心流程各走一次；每個外部整合用一個低風險動作確認——
   這是在正式站對真實第三方動手，由［負責人］執行或逐項核准
8. **開新站的排程**：先依 `hosted-apps.md` §2.1「排程最後才開」步驟 2 的紀錄，把目的地改回正式值
   （［負責人］執行或逐項核准）；owner 確認後由［負責人］建平台排程、開 app 的總開關；
   `scripts/aigo_cron_health.py --app <入口 app-id> --expect-action <action>` 綠燈；工作本身的驗證分兩種：
   - 標「安全」或重跑無害（冪等、不對外）的工作：由［負責人］執行或逐項核准**單支手動觸發**一次
     （`hosted-apps.md` §2.1 步驟 3、「手動觸發不要佔正式時段」；觸發要用排程金鑰，AI 不經手），回 app 的執行結果表確認成功
   - 會寫業務資料或對外（寄信、推播、寫第三方）的工作：**不做手動觸發**——手動觸發不佔正式時段，自然週期還會再跑一次，
     等於在正式環境重複發送。改在 §9 看它的第一個自然週期，並安排人盯著
   - 不等每天或更久才跑的工作的自然週期，以免把切換拖住
9. **［負責人］宣布完成、通知使用者**：新站開始正式服務；**原站不重新開放**，維持唯讀或停機到 §9 退場

**回滾**：觸發回滾條件時，由［負責人］依序：
1. **先擋住新站所有寫入**：`internal` 的收回正式角色；`public` 的把「切換前只放行名單」開關打回去
   （`public` 的 `access_role_ids` 本來就必須為空，沒有角色可收，`hosted-apps.md` §6）。
   **入站端點也要擋**：webhook、推送、轉發 action 是靠金鑰或簽章進來的，名單開關擋不到——app 要有涵蓋這些端點的寫入閘或維護開關
   （階段 B 的程式改動）。做不到的，第 3 步要在第 4 步改完登記後**再補抓一次差異**
2. **停新站排程**（平台排程停用、app 總開關關閉）
3. **處理新站期間寫入的資料**：照階段 E 選定的方式，不臨時決定（入站端點擋不住的，第 4 步之後再補抓一次）
4. **外部登記照清單改回**，有自訂網域的改回 DNS
5. **最後才打開原站**：解除唯讀、恢復原站排程與留在原機的排程

## 9. 階段 G：觀察與舊站退場

**觀察期**（建議 1～2 週，依使用頻率調整）：

- 每天看一次：`scripts/aigo_cron_health.py --app <入口 app-id>`、app 自己的執行結果表、`hosted-apps.md` §8 的日誌、使用者回報
- 每支排程工作的**自然週期**至少成功一次（每週、每月的也要等到，觀察期因此可能超過 1～2 週），才算觀察期完成；
  會對外的工作第一次自然週期要有人盯著
- 原站保留**唯讀或停機但不刪**，資料與設定都留著，回滾才有地方回

**退場**（觀察期無未解問題、owner 同意後；以下都由［負責人］執行）：

- 刪除原站的排程與服務；撤銷只給原站用的金鑰、OAuth client 的舊回呼網址、舊的推送訂閱
- 留在原機的排程與微服務：改指新站的已驗證，退役的關掉
- 原站資料最後備份一份，存放位置與保留期寫進計畫
- 舊網域、DNS、帳單停止
- 階段 A 第 5 項的 CI 檢查（禁止舊平台網域字樣）保留

**通過條件**：退場清單每項打勾；計畫裡記下原站備份的位置與保留期限。
